Как работает асинхронность:

Uvicorn запускает ASGI-приложение внутри event loop. 
Async endpoint'ы выполняются конкурентно: coroutine работает до точки await, приостанавливается, если ожидает незавершённую async-операцию, 
а event loop в это время запускает другие готовые задачи. Когда ожидаемая операция завершается, coroutine снова становится runnable. 
Блокирующую или CPU-bound работу нельзя просто обернуть в await — её нужно отдельно выносить в thread/process pool или другой 
worker-механизм.

Когда возникает ошибка, она перехватывается exception_handler, который регистрируется 

@app.exception_handler(Exception)
async def value_error_handler(request: Request, exc: Exception):
    return JSONResponse(
        status_code=500,
        content={
            "error": str(exc),
        },
    )

то вызывается отправка ответа через ASGI, а midlware на обратном пути игнорируется, там можно сделать
через finally какое-то логирование, но основную работу делает ASGI send

Нюанс:
Middleware начинает выполняться раньше exception handler. При исключении call_next() пробрасывает исключение обратно в middleware, 
поэтому except/finally middleware срабатывают раньше exception_handler. После выхода исключения из middleware Starlette's exception 
handling layer вызывает зарегистрированный handler и формирует HTTP Response.

Про request.state
`request.state` — это встроенное в Starlette/FastAPI **хранилище произвольных данных, привязанное к 
конкретному HTTP-запросу**: middleware, dependencies и endpoint могут записывать туда значения 
(`request.state.user = user`) и читать их позже; данные живут только в рамках этого request и не 
являются глобальным кэшем, поэтому `request.state` удобно использовать, например, для ручного 
request-local кэширования результата `get_current_user`, чтобы повторно не обращаться к БД.


Про обновление одиночных строк на изолированных транзацкиях
Суть FOR UPDATE — прочитать строку и одновременно заблокировать её до конца текущей транзакции.

Ту же проблему можно решать через изоляцию транзакций
FOR UPDATE — это явная пессимистическая блокировка: транзакция говорит PostgreSQL «я собираюсь работать с этой строкой», 
PostgreSQL блокирует её, а конкурирующая транзакция ждёт. В твоём переводе это выглядит как SELECT ... FOR UPDATE → проверить 
баланс → UPDATE → COMMIT. Это простой и локальный способ защитить конкретный ресурс.

SERIALIZABLE — более общий уровень изоляции: PostgreSQL не ставит все транзакции в очередь, а позволяет им работать параллельно 
и отслеживает конфликтующие зависимости. Если обнаруживает, что успешное выполнение обеих транзакций невозможно представить как 
последовательное выполнение, он откатывает одну с serialization failure; приложение должно повторить транзакцию. То есть FOR UPDATE 
предотвращает конфликт заранее блокировкой, а SERIALIZABLE допускает конкуренцию и обнаруживает конфликт постфактум.

Когда использовать:
FOR UPDATE — когда ты знаешь, какие конкретно строки собираешься изменить, и хочешь не допустить одновременной работы с ними. 
Например: перевод денег, списание товара со склада, резервирование места, изменение счётчика. Это обычно самый понятный выбор.

SERIALIZABLE — когда корректность зависит от нескольких чтений/условий во всей транзакции, и трудно вручную перечислить, что 
именно нужно блокировать. Например: сложные проверки инвариантов, где несколько таблиц/строк должны рассматриваться как единое 
состояние. При этом нужно обязательно реализовать retry при serialization failure.
